### Q3
>How many functions call gethostbyname?

![](/assets/img/malware-analysis/Pasted%20image%2020260707212453.png)

There are 18 cross-references shown for `gethostbyname`, but there are only 9 actual call sites. This is because IDA displays two references for each imported function call through the IAT: 
a procedure reference (`p`) for the call itself and a read reference (`r`) because the call reads the function pointer from the Import Address Table (IAT). Thus, each `call ds:gethostbyname` appears twice in the xrefs list, even though it represents a single call instruction.

Looking at the xrefs, we can see that `gethostbyname` is called from only in **7 different functions:  
- `sub_10001074:loc_100011AF`
- `sub_10001074+1D3`
- `sub_10001074+26B`
- `sub_10001365:loc_100014A0`
- `sub_10001656+101`
- `sub_1000208F+3A1`
- `sub_10002CCE+4F7`

### Q8
>What is happening in the area of code that references \cmd.exe /c?

The string has a single cross-reference.

![](/assets/img/malware-analysis/Pasted%20image%2020260707225812.png)

Following this cross reference,it retrieves the Windows system directory and constructs the command interpreter path. Depending on the operating system, it uses either `cmd.exe /c` or `command.exe /c`. 
The `/c` switch instructs the interpreter to execute the supplied command and terminate afterward.

![](/assets/img/malware-analysis/Pasted%20image%2020260731232136.png)

It continuously receives commands from the remote client over the socket connection. Incoming bytes are assembled into a command string stored in `Buf1`

![](/assets/img/malware-analysis/Pasted%20image%2020260731232342.png)

It first checks whether the received command is one of its built-in commands. If a match is found, it executes the corresponding internal function. Otherwise, the command is handled by the Windows command interpreter `cmd.exe /c`

![](/assets/img/malware-analysis/Pasted%20image%2020260731232710.png)

And these strings identify the malware's remote shell and display session information before processing commands.

![](/assets/img/malware-analysis/Pasted%20image%2020260731233515.png)
### Q9
>In the same area, at 0x100101C8, it looks like dword_1008E5C4 is a global variable that helps decide which path to take. How does the malware set dword_1008E5C4? (Hint: Use dword_1008E5C4’s cross-references.)

Examining the cross-references to `dword_1008E5C4`, we find three references. One of them writes to the variable, while the other two only read it.


![](/assets/img/malware-analysis/Pasted%20image%2020260707231137.png)

The write reference assigns the return value of `sub_10003695` to `dword_1008E5C4`.

![](/assets/img/malware-analysis/Pasted%20image%2020260707231525.png)

Analyzing `sub_10003695` shows that it calls `GetVersionExA`.

![](/assets/img/malware-analysis/Pasted%20image%2020260707234935.png)

`GetVersionExA` fills an `OSVERSIONINFOA` structure.
The function compares `VersionInformation.dwPlatformId` against `2`, which corresponds to the Windows NT platform.

![](/assets/img/malware-analysis/Pasted%20image%2020260712015616.png)

On the NT windows platform the value of dwPlatformId is 2.

![](/assets/img/malware-analysis/Pasted%20image%2020260712023244.png)

If the comparison succeeds, `setz al` sets `AL` to `1`, otherwise, it returns `0`.

Therefore, `dword_1008E5C4` stores whether the operating system belongs to the Windows NT family.

### Q17
> Search for usage of the in instruction (opcode 0xED). This instruction is used with a magic string VMXh to perform VMware detection. Is that in use in this malware? Using the cross-references to the function that executes the in instruction, is there further evidence of VMware detection?

Searching for the `0xED` opcode reveals the following instruction:

![](/assets/img/malware-analysis/Pasted%20image%2020260724234740.png)

The `in eax, dx` instruction reads 32 bits from the I/O port specified in `dx`. In this case, however, it is used as part of the VMware backdoor detection technique. The code loads the magic value `'VMXh'` into `eax`, sets `dx` to the VMware I/O port (`'VX'`), and executes the `in` instruction.

If the program is running inside VMware, the hypervisor responds by placing `'VMXh'` into `ebx`, causing the comparison to succeed.

![](/assets/img/malware-analysis/Pasted%20image%2020260725000447.png)

Further evidence of VMware detection is the string:  `text Found Virtual Machine, Install Cancel.`

which is referenced by the detection routine. If a virtual machine is detected, the malware displays this message and cancels the installation.

![](/assets/img/malware-analysis/Pasted%20image%2020260725000802.png)

### Q19
>If you have the IDA Python plug-in installed (included with the com-mercial version of IDA Pro), run Lab05-01.py, an IDA Pro Python script provided with the malware for this book. (Make sure the cursor is at 0x1001D988.) What happens after you run the script?

The original script uses `ScreenEA()`, which did not work in my case, so I modified it to use `idc.here()` instead.

```python
# sea = ScreenEA()

# for i in range(0x00,0x50):
#         b = Byte(sea+i)
#         decoded_byte = b ^ 0x55
#         PatchByte(sea+i,decoded_byte)

import idautils 
import idaapi

sea = idc.here()

for i in range(0x00,0x50):
    b = ord(idaapi.get_bytes(sea+i, 1))
    decoded_byte = b ^ 0x55
    ida_bytes.patch_byte(sea+i,decoded_byte)

```

Running the script xor decodes the data, converting it into readable strings.

### Q21
>Open the script with a text editor. How does it work?

The script decodes an xor encoded data block at the current cursor location in IDA.

It first gets the current address using `idc.here()`. Then, it loops through the next `0x50` bytes, reading each byte with `idaapi.get_bytes()`. Each byte is xored with the constant `0x55`, and the decoded byte is written back into the database using `ida_bytes.patch_byte()`. 

As a result, the encrypted data is replaced with its decoded form, making the hidden strings readable in IDA.

The decoding algorithm is: 
decoded_byte = encoded_byte ^ 0x55
